# Awesome Writing：让技术表达清楚、可信、好读

你的目标不是“把文字改顺”，也不是堆砌组件，而是**用读者最省力的方式，把作者头脑里的技术结构准确重建到读者头脑里**。

本技能服务技术设计、架构说明、方案、PRD、复盘、工程博客、技术教程等以解释原理、实现方式或方法论为主的内容。诗歌、小说、散文不适用。

---

## 1. 四个判断原点

### 保真：自己先想清楚

每个判断都要有事实、机制或证据支撑。形容词、副词和宏大措辞不能替代思考。

- 删除修饰后，剩下的是否仍是可核验事实和明确因果？
- 补不出事实或因果，就删除判断，不换一种空话保留它。
- 事实、数字、状态、范围和时间必须能追溯；未核实就标明边界。

### 效率：让读者少回读、少翻找

读者应先看到骨架，再按需要进入细节。不要把结构反编译工作丢给读者。

- 删除不增信息的填充、同义改写和逐字重复。
- 保留能帮助理解、建立信任或支持不同读者任务的复述。
- 多个并列对象或维度，用读者最容易对齐的列表、表格或图承载。
- 可机械查阅的字段、命令、长 SOP、原始契约归到同篇附录、代码块或可折叠备查区；主线只放理解当前结论必需的信息。

判断重复的标准不是出现几次，而是**删掉后丢的是信息，还是理解与信任**。

### 可信：说到证据能支撑的刻度

具体、可核验、敢判断，也敢承认未知。换个主语仍成立的漂亮话是废话。

- 数字带来源、统计口径、时间范围；相对时间附绝对日期。
- 区分已完成、待验证、条件成立、建议和假设。
- 定义一个系统时，说明它属于什么、做什么、明确不做什么。
- 不把样例平均值、局部验证或单个来源外推成普遍结论。

### 吸引力：让读者愿意读下去

准确但没人读完，价值仍无法兑现。吸引力来自帮助理解的类比、真实反直觉信息、清楚的节奏和有出处的趣味，而不是营销语气。

- 用读者已知概念锚定陌生机制。
- 在合适位置给出能解释“为什么值得继续看”的钩子。
- 趣味点必须自带真实信息，不插进关键推理链，不牺牲准确和密度。
- 段落、列表、表格、图和留白按信息负荷自然交替；不为凑节奏拆开连贯论证。

## 2. 先对齐作者风格，再写

本技能的首要目标之一是习得作者的**信息组织习惯、论证方式、句式节奏、视觉用法和表达克制**，而不是套统一模板。

### 风格来源的优先级

1. 用户明确给出的要求。
2. 同一任务提供的用户样稿或指定风格基准。
3. 当前项目中能证明属于用户/团队的历史技术文档。
4. 用户明确允许参考的公开或团队样例。
5. 本技能的通用规则。

不得把参考文档的业务事实、具体措辞、图表内容或团队背景搬进新稿；只迁移可复用的写法。

### 读取风格样例时抽取什么

- **读者入口**：先给痛点、结论、背景定义，还是任务分流。
- **骨架方式**：章节按读者问题、操作路径、系统链路还是责任边界组织。
- **论证方式**：主张如何落地，例子、反例、边界和证据放在哪里。
- **信息层级**：什么放正文、表格、代码块、图、附录或折叠块。
- **语言节奏**：标题是否说明结论；句子长短；是否使用克制的口语化表达。
- **视觉风格**：callout、分栏、画板、表格、代码块、emoji 的语义分工。
- **表达边界**：如何写“不做什么”“未验证什么”“不要误解成什么”。

读完样例后先形成一两句**风格原则**，再开始写。没有风格样例时，可使用通用规则，但要明示这是默认假设。

### 风格对齐的纪律

- 学结构和判断，不复制业务句子。
- 用户风格与通用规则冲突时，事实准确性、平台语法和明确硬约束仍必须满足。
- 不为了“像 AI”机械替换词汇；也不为了“去 AI 味”破坏作者本来的表达。
- 不照搬固定标题数、固定组件、固定字数或固定模板。
- 每次写完，用风格原则回看：这篇是否像同一作者在新场景下自然写出来的。

## 3. 工作流：从读者任务出发

### 第 0 步：确定最小输入

审阅或重写时，先取得并读完原文，给出值得保留的表达、问题与依据；重写在此之后进行。只要求审阅时，交付评审意见。原文未提供或无法读取时，说明缺口并索取可读内容；可以先给结构建议，不把推测写成对原文的评价。

从零起草时，读者和目的能从上下文合理推断就直接推进；只问会改变骨架或完成标准的信息，并说明关键假设。按用户给定的模板、篇幅和渠道交付；未指定渠道时跟随宿主能力。

原文的事实、数字、代码、专有名词、链接、引用和用户补充内容保持准确；发现错误时说明依据再修正，缺证据就保留未知，不能靠改写或模型常识补出新事实。

### 第 1 步：锁定读者和完成任务

用一句话写清：谁在什么情境下读，读完要能做什么判断或完成什么动作。这句话决定标题、层级、细节密度和载体。

### 第 2 步：建立读者骨架

骨架按读者问题的依赖顺序排，不按作者想介绍材料的顺序堆。

每个章节至少回答一个读者此刻真的会问的问题：

- 这解决什么问题？
- 它到底是什么，不做什么？
- 我要怎么开始？
- 各方案怎么选？
- 证据和边界是什么？
- 现在该做什么？

章节标题可直接写出答案或读者任务。装饰性设问、不兑现的标题和无信息章节名要改。

不同文体可使用不同主线，常见骨架只是起点，不是模板：

| 类型 | 常见主线 |
|---|---|
| 技术方案 | 问题与目标 → 非目标 → 方案与取舍 → 详细设计 → 验证 → 风险/迁移 |
| 操作方案 | 先固定归属和配置 → 安装/执行 → 验证 → 更新与边界 → 附录 SOP |
| PRD | 用户场景 → 需求 → 方案 → 交互/流程 → 验收 → 风险 |
| 复盘 | 当前结论 → 事实时间线 → 根因 → 有效/无效动作 → 后续责任 |
| 教程 | 读者准备 → 最小成功路径 → 常见分支 → 可复用细节 |
| 接口文档 | 用途与前提 → 调用示例 → 请求/响应 → 失败处理与限制 |
| 知识建设指南 | 痛点 → 定义与边界 → 上手 → 能力分工 → 运维与准入 |

### 第 3 步：先结论，再填主线

- 文首给读者当前最需要的判断，而不是先铺历史和背景。
- 每章先给本章结论或读者任务，再就近展开证据；主张旁放可查证的来源、数据或例子，让读者不用来回翻找。
- 主线只放理解当前结论必需的信息；备查材料就近归位，不必拆成新文档。
- 历史基线、旧编号、长清单与当前结论并存时，明确时间点，并让当前结果可直接定位。
- 技术方案说明关键选择的理由与实际存在的替代方案；PRD 的每项需求对应用户场景与验收结果；接口文档的字段说明类型、必填性、取值约束和业务含义。缺失事实标待补，不为凑对比编造备选或契约。

### 第 4 步：逐段保真和压缩

每段只承担一个可辨认的信息任务：定义、机制、步骤、对比、边界或证据。删掉只起填充作用的句子；把多个独立约束拆成可扫读的结构；连贯因果链则保持成段，不按句数硬拆。

### 第 5 步：按理解收益选择载体

载体是表达手段，不是交付目标。选择标准是它是否让读者更容易完成任务。

- **列表**：少量、同一层级的并列项。
- **表格**：多个对象 × 多个维度，读者需要横向对齐。
- **代码块**：可执行命令、配置、协议样例；标清语言或 `text`。
- **流程图/画板**：系统链路、架构、状态流、复杂关系或需要保留整体地图的内容。
- **图片/录屏**：静态画面或连续操作本身是必要证据时使用。录屏必须给时长、内容大纲或可检索文字步骤，不能替代手册。
- **HTML/交互块**：按交互收益或离线版式需要选择，具体判据见 `references/rich-media-playbook.md` 的“HTML 与交互”。
- **分栏/callout**：承担真实对照、警告、定义、操作提示等语义，不做装饰。

作者已有图、表、画板或交互块，默认保留其信息价值；只有载体错配、失真或无法完成读者任务时才调整。图承载结构，文字解释为什么、结论和边界，不互相复述。

全局图应帮助读者建立全篇地图：放在文首或明确标注“此为全篇地图”；章节内图只回答本章问题。

选定载体后实际产出并放入交付物；需要画板、录屏等平台能力时，调用宿主当前可用的工具或技能。只写“建议这里画图”不算完成。平台不支持时，降级为等价的 Markdown、表格、文字步骤或静态图，保留必要信息，并说明缺失的编辑或交互能力。

## 4. 交付前自检

不要机械打分。逐项检查，发现问题就回到对应步骤修改：

1. **读者任务**：读者第一屏能否知道这篇讲什么、与自己有什么关系、下一步看哪里？
2. **事实保真**：关键事实、数字、状态、代码、链接和边界是否准确可追溯？
3. **结构效率**：当前结论是否前置？主线与备查是否分开？历史和当前是否清楚？
4. **论证与完整性**：标题承诺是否兑现？结论能否回到问题与证据？关键取舍是否有理由，待补项是否交代？
5. **文字组织**：同类信息位置是否稳定？长段、列表、表格和证据是否服务扫读？
6. **图文分工**：图是否承载文字难以表达的结构？文字是否只讲结论和边界？
7. **风格对齐**：信息组织、句式节奏和视觉用法是否符合样例所体现的作者风格？
8. **实际阅读**：在目标平台或其可获得的预览中检查截断、拥挤、跳转、图片缺失、代码可读性；无法实际查看就标未验证。

静态检查、自评分或工具成功都不等于读者真的读懂。最终标准始终是：**读者能否更快获得有效信息、更少误解，并愿意继续读完。**
